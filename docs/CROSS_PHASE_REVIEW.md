# Cross-phase implementation and research gates

Review date: October 4, 2026. Requested by Hamza before further dependent implementation. This report covers the product's current feature families, the approved phase plans, current source, focused verification and primary documentation. It is not a completed penetration test, usability study, load test or live provider certification. Phase work remains in progress; each new increment must rerun its affected checks.

## Recommendation

Keep the approved product breadth and the modular FastAPI/API-worker architecture. Finish the trust and recovery boundaries before spreading new interactions across the interface. Jira, Slack, GitHub and supported LinkedIn functions remain core. The highest-priority revisions concern demo isolation, exact delivery semantics, authority and concurrency, truthful extraction presentation, privacy lifecycle and free-hosting constraints.

Use three dispositions: **revise now** for demonstrated implementation/design gaps; **research or verify first** where provider/platform or rendered evidence is required; **later** for enhancements whose dependencies are not ready. Blocking means a release or dependent implementation gate, not necessarily a demonstrated vulnerability.

## Phase 2: data, access and lifecycle

| Feature | Priority / disposition | Required revision or research | Acceptance evidence |
| --- | --- | --- | --- |
| Transcript capture/upload | Important / verify first | Preserve byte/UTF-8 bounds, source metadata and unique meeting/revision behavior. Distinguish retrying a failed upload from intentionally replacing a transcript. No implicit import from a meeting provider. | Oversize, malformed encoding, duplicate click, replacement and interrupted indexing tests. |
| PostgreSQL migrations | Blocking / verify first | Apply only forward additive changes after retention/drift checks. Test the actual upgrade chain, not metadata.create_all alone. Keep runtime upgrade separate from disposable test schemas. | Existing Jira grants, legacy previews and other retained rows survive; Alembic agrees with models. |
| Transactions and lock ordering | Blocking / revise now | Establish one ordering across user/membership, provider account, meeting, destination and operation paths. Inspect Slack reconnect versus action handling. Release rejected test transactions before separate workers. | PostgreSQL reconnect/action, revoke/send, duplicate approval and deadlock regressions with bounded waits. |
| Public visitor isolation | Blocking / implement before release | Unique visitor authority and synthetic workspaces, bounded quota/expiry, no membership in private workspaces and no ability to attach live credentials. Global PUBLIC_DEMO_MODE alone is insufficient. | Two independent browsers cannot read/change each other's records or private records; expiry denies work/jobs. |
| Invitations | Blocking for private onboarding / research and implement first | Use email-bound, hashed, expiring, single-use invitations. Existing accounts must authenticate before accepting; an invitation must not overwrite a global account password. Manual invite sharing needs clear UI. | Wrong identity, replay, expired/revoked invite, concurrent acceptance and invited role tests. |
| Password recovery | Blocking for private release / research first | Do not let a workspace owner reset a global account used elsewhere. Use account-bound recovery with neutral public responses and session/token invalidation. Manual operator issuance is distinct from an implemented email flow. | Single use, expiry, wrong account, revoked sessions and no account enumeration; no unauthorized email send. |
| Restricted meetings and directory | Blocking / verify first | Roles alone are insufficient: check workspace, meeting visibility and current relationships at every read/export/write. Confirm participants explicitly; separate external mappings from name similarity. | Viewer/editor/reviewer/owner matrix, same-name people, restricted receipts/history and revoked mappings. |
| Privacy export, archive and deletion | Blocking for real data / define before implementation | Archive is reversible, not erasure. Define export authority and deletion of transcripts/chunks/indexes/drafts/plans/credentials. Preserve a minimal operational tombstone for uncertain writes without keeping unnecessary private content. | Complete synthetic lifecycle including pending jobs, uncertain delivery, backups and retained audit metadata. |
| Indexes and pagination | Important / measure first | Bound query results and use stable ordering/cursors. Current daily-plan candidate list has a hard cap; client-side search cannot search records the server did not return. | Representative EXPLAIN/query counts and server-side pagination/truncation UX. |

OWASP recommends deny-by-default authorization, checks on every request and explicit resource/role test matrices. Recovery guidance requires expiring single-use tokens and neutral account responses. PostgreSQL documents consistent lock acquisition as a primary defense against deadlocks. References: [authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [PostgreSQL 17 locking](https://www.postgresql.org/docs/17/explicit-locking.html).

## Phase 3: extraction, jobs and Slack

| Feature | Priority / disposition | Required revision or research | Acceptance evidence |
| --- | --- | --- | --- |
| Local AI extraction | Important / research and measure first | Retain the current model until a versioned synthetic corpus establishes better supported extraction at acceptable CPU latency/memory. Valid JSON and valid citation IDs do not prove that cited text supports the assertion. | At least 24 cases across departments: unsupported claims, negation, completed/hypothetical work, dates/numbers, multilingual text, ambiguous owners, long transcript tail and prompt injection. |
| Extraction confidence | Important / revise now | Current rules use confidence=0.6 and OutcomeCard displays a percentage. Treat it as an uncalibrated heuristic, never measured accuracy. Prefer evidence/confirmation status or an explicit explanation. | UI does not imply probabilistic accuracy; raw model quality is evaluated separately from deterministic corrections. |
| Model/rules fallback | Important / revise now | Workbench has processing mode in the job result but currently displays only created count. Show rules/mixed/local-model mode and meaningful warnings. A hosted rules demo must not imply model inference or on-device privacy. | Model outage/truncation/no-outcome paths remain useful and visibly truthful. |
| Jobs/recovery | Blocking / verify first | Durable intent, current authority and lease ownership must survive worker crashes. Retrying computation differs from retrying a provider write. Never drive retries from animation or a receipt refresh. | Crash before/after intent, stale source, revoked user, expired lease and partial delivery tests. |
| Slack message create/update | Important / verify first | Distinguish known rejection from uncertain write; require channel/installation authority and exact approved content. Updates apply only to M2O's permitted messages and must detect remote drift. | Synthetic 429/403, timeout, malformed success, duplicate approval, read-only reconciliation and changed target. |
| Slack identity/actions | Blocking / revise and verify first | Signed requests identify a Slack actor, not automatically an M2O user. Keep browser confirmation, account generations, one-use modal context and per-user plan authorization. | Replay, wrong actor/team/app/session, reconnect, membership revocation and concurrent modal submissions. |
| Slack acknowledgement | Blocking for live actions / research and measure first | All work before acknowledgement needs one total deadline, not only individual request timeouts. A sleeping free service cannot reliably meet the deadline. Keep interactive readiness distinct from message delivery readiness. | Warm endpoint under contention returns within the required time; cold/sleeping deployment keeps actions disabled. |
| Meeting capture/import | Important / scope separately | Slack capture is explicitly submitted text. Zoom/Meet import requires existing artifacts, authorized scopes, source IDs and idempotent import revisions. It is a separate source adapter, not inferred from a delivery app. | Controlled artifact availability, pagination, missing transcript, repeated import and permission-denial cases before enabling. |

Ollama supports schema-constrained output and recommends lower temperature; this establishes format controls, not factual correctness. Prompt-injection defense must include boundaries and validated output, not only a system prompt. Slack requires an HTTP acknowledgement within three seconds. References: [structured outputs](https://docs.ollama.com/capabilities/structured-outputs), [OWASP prompt injection](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html), [Slack interactions](https://docs.slack.dev/interactivity/handling-user-interaction/).

## Phase 4: Jira, GitHub and LinkedIn

| Feature | Priority / disposition | Required revision or research | Acceptance evidence |
| --- | --- | --- | --- |
| Exact approval/shared receipts | Blocking / verify first | Persist exact source versions, destination generation, payload/hash, actor and expiry. Recheck before sending. An existing resource, a successful send and actual task completion are different facts. | Changed source/destination/role, repeated approval, restricted disclosure and refresh/history tests per adapter. |
| GitHub duplicate detection | Blocking for exact receipt claims / revise now | Source review: worker accepts a marker match as existing without comparing approved title/body/labels/assignees. Same outcome/version with changed evidence or manual remote edits may not match the preview. Preserve duplicate prevention while exposing exact-match versus conflict. | Matching existing content is recognized; changed content is not silently called exact completion or overwritten; no second POST. |
| GitHub success content | Important / revise now | Phase 4's official-document review found labels/assignees can be silently omitted when repository permissions are insufficient. HTTP 201 with a number/URL alone does not prove every reviewed field was applied. Verify the returned controlled fields and retain a resource receipt if content differs. | Dropped labels/assignees or changed title/body produce an explicit known-resource conflict and stop the batch; no resend or overwrite. |
| GitHub scope and recovery | Important / verify first | Keep owner-bound workspace destinations in addition to operator allowlists. Searches include closed issues, exclude pull requests, validate canonical URLs and are bounded. A failed/incomplete scan must not permit a write. | Workspace isolation, multi-page duplicate markers, scan timeout, permission/rate-limit distinction and uncertainty tests. |
| Jira create/update | Important / research first | Revalidate issue type/required fields and external assignee mapping. The remote updated-time read before PUT detects prior changes but is not demonstrated atomic compare-and-swap protection against edits between read and write. Limit changed fields and describe the remaining race honestly. | Required custom fields, changed issue/project/permissions, remote-edit conflict and partial/uncertain update tests. |
| OAuth refresh/revocation | Blocking / verify first | Rotating grants need serialized refresh, generation/version checks and atomic replacement. Reconnection/disconnect/offboarding must invalidate old proposals and action identities. | Concurrent refresh, invalid grant, token replacement, reconnect while queued and revoked owner tests. |
| LinkedIn identity vs publishing | Blocking / verify first | Keep self-profile OIDC distinct from member-post authorization and encrypted retained credentials. Posting requires actual product/scope approval, verified author ownership and explicit public disclosure. Draft functionality can work independently. | Consenting-user author, wrong subject/app/scope, expired/revoked grant, stale draft and public approval tests. |
| LinkedIn uncertain writes | Blocking / preserve boundary | Posting scope does not grant general member-post retrieval. Without permitted read access, a timeout may remain uncertain. Never promise automatic reconciliation or resend from an absent receipt. | Crash/timeout retains uncertainty, no blind retry and UI provides a truthful manual resolution path. |
| LinkedIn outreach/context | Important / preserve scope | Useful local outreach drafts and human-confirmed context are valid. Arbitrary name lookup, professional-history enrichment and automatic lead messaging are not established by current grants. | UI distinguishes local draft from delivery and names the actual supported capability. |
| External status synchronization | Important / later unless contract complete | Keep M2O personal progress, provider workflow state and review approval independent. Read-only status needs observed_at/source. Any future write-back needs explicit mapping, authorization and duplicate/conflict rules. | No delivery or external close silently completes/reopens/approves M2O records. |

GitHub's issues collection also includes pull requests. Atlassian rotates refresh tokens and requires retaining replacements. LinkedIn distinguishes member write permission from restricted read permission and uses an explicit version header. References: [GitHub issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues), [Atlassian 3LO](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/), [LinkedIn Posts](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-09).

W3C requires controls for qualifying automatic motion, appropriate hover/focus behavior, and defines a minimum target-size criterion in WCAG 2.2. Aim to meet these as concrete acceptance checks rather than declaring compliance from a component library. Render documents sleeping services, temporary free databases and no free background workers. References: [motion control](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html), [hover/focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html), [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Render Free](https://render.com/docs/free).

2. Finish and test the supported provider contracts before frontend reliance, with live activation explicitly separate.
3. Implement visitor isolation, invitation/recovery authority and privacy lifecycle against the defined boundaries.
4. Complete frontend access/provider flows; verify all departmental journeys, deep links, failure states and media in rendered browsers.
5. Run current broad verification, disposable hosted-runtime/recovery checks and model evaluation. Document unresolved budget/account/product dependencies.
6. Prepare a concrete release candidate and maintenance runbook. Deployment, external account configuration and live writes still require exact authorization.
